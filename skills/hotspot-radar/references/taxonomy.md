# 排序、去重与归类准则

脚本只给你归一化后的条目，**不做任何判断**。这份文件讲清楚该怎么判断 ——
否则最容易的错法就是「按 `heat` 降序」，得到一张被百度热搜统治的榜。

> **唯一的例外是 `fetch.py` 的 `--author` / `--grep`。** 那是**确定性子串过滤**
> （「这个字符串在不在」，可复现、不含判断），所以它放在抓取侧。
> 它不会替你判断相关性 —— 下面这些准则一条都没少。

---

## 1. 排序：永远不要直接按 `heat` 跨源排序

`heat` 是各源的原生数值，量纲完全不同：百度热搜指数是百万~千万级，
V2EX 的 `heat` 是回复数（几十），GitHub Trending 是今日新增 star（几百）。

**直接按 `heat` 排，前 20 条会全部来自百度。**

### 可用的做法，按场合选

**A. 按 `rank` 排序（最省事）**

`rank` 是「在它自己那个源里排第几」。跨源比 `rank` 是合理的：
每个源的 rank=1 都代表「这个源当下最热的一条」。

```
按 rank 升序 → 每个源的头条自然浮到前面
```

适合「我就想看看各方头条」的速览场景。

**B. 源内归一后再混合（更准）**

把每个源的 `heat` 映射到 0~1（`(h - min) / (max - min)`，或直接按源内排名取
`1 - rank/count`），再加权：

```
score = 0.5 * norm_heat_in_source + 0.3 * (1 - rank/count) + 0.2 * recency
```

`recency` 用 `publishedAt` 相对现在的小时数取衰减（比如 `exp(-age_hours/24)`）；
`publishedAt` 为 `null` 的给一个中性值（0.5），**不要当成 0 或 1** ——
百度热搜本来就没有时间字段，当成 0 会让整个源沉底。

**C. 按来源分组展示（最不容易出错）**

不做跨源排序，直接「B站：…／V2EX：…／36氪：…」分块列。
当用户问的是「今天有什么热点」而不是「排个序」时，这个反而最好用，
也最诚实 —— 你没有假装一个不存在的统一尺度。

### 时间衰减

热点监控里「昨天爆的」和「一小时前爆的」不是一回事。
只要条目有时间就用它加权；注意**百度热搜、GitHub Trending 没有 `publishedAt`**，
这类源只能靠 `rank`。

---

## 2. 跨源去重

同一个事件会在多个源出现（比如某模型发布，36氪、InfoQ、V2EX 各有一条）。
脚本的 `dedupe()` **只去同一源内的重复 id**，跨源合并是你的活儿。

### 判据（从强到弱）

1. **URL 同源不同参** —— 归一化后相同（脚本已处理）。
2. **标题高度相似** —— 归一化后（去标点、去空格、转小写）相似度高。
   中英文标题不会互相匹配，别指望。
3. **实体重合** —— 标题里同时出现同一组专有名词
   （公司名 + 产品名 + 数字，如「OpenAI」「GPT-5」「发布」）。

### 合并时保留什么

- `url` 用**信息量最大**的那个（原文 > 转载 > 聚合页）
- `sources` 列成数组，多源命中本身就是**热度信号**，要显式说出来
  （「这条在 3 个源同时出现」比单看某一条更有说服力）
- `heat` 不要相加（量纲不同），但可以记「出现在 N 个源」

### 别过度合并

只共享一个泛词（「AI」「大模型」）的两条标题**不是**同一件事。
宁可不合并，也别把两条不同的事件揉成一条 —— 合并错了用户看不出来，
但会丢掉一条真实热点。

## 3. 归类

给条目打标签时，用这套（可按用户关注领域调整）：

| 类别 | 识别信号 |
|---|---|
| 模型发布/更新 | 版本号、`发布`、`开源`、`权重`、模型名 |
| Agent / 应用 | `Agent`、`智能体`、`工作流`、`MCP`、工具调用 |
| 开源项目 | GitHub 来源、`star`、`repo`、`开源` |
| 融资/商业 | `融资`、`估值`、`收购`、`IPO`、`营收` |
| 政策/监管 | `监管`、`法案`、`合规`、`备案`、`安全审查` |
| 研究/论文 | `论文`、`arXiv`、`benchmark`、`SOTA` |
| 硬件/算力 | `GPU`、`芯片`、`算力`、`数据中心`、具体型号 |
| 行业观点 | 访谈、复盘、预测、长文分析 |
| 争议/事故 | `翻车`、`泄露`、`下架`、`诉讼`、`封号` |

一条可以属于多类；不要为了整齐而硬塞。

## 4. 可信度：你能判断什么，不能判断什么

**先把话说死：脚本不做任何真假判断，你也没法凭这份 JSON 验证一条消息是不是真的。**
你唯一能做的是**可信度分级** —— 从元数据（源类型、几源印证、措辞、信息量）
给出一个诚实的置信度，并**说清你是凭什么这么说的**。

判断者就是你自己（Agent），不额外调任何模型。下面是你手上真正有的几个信号。

### 4.1 源分级 —— 第一依据，不是热度

| 级别 | 源 | 意味着 |
|---|---|---|
| **一手** | `github`（仓库本体）、`ruanyifeng`（本人周记） | 事件发生的地方 |
| **二手可靠** | `infoq`、`36kr`、`solidot`、`sspai`、`hn`、`lobsters` | 有编辑流程的媒体/社区 |
| **低信噪** | `baidu`、`bilibili` | 标题党、营销号、转述再转述 |

同一条消息，出自 `infoq` 和出自 `baidu`，可信度不是一回事 —— **别用热度补可信度**。

### 4.2 交叉印证 —— 你手上最强的信号

同一件事出现在**几个互相独立的源**，是这份数据里最硬的证据。
而它在去重那一步（§2）就已经算出来了，别浪费：

| 命中情况 | 该怎么措辞 |
|---|---|
| ≥3 源，且含至少一个二手可靠源 | 「多家报道」—— 可以当事实陈述 |
| 2 源 | 「据 A、B 报道」 |
| 1 源，且是**低信噪源** | 「有消息称…**目前只有百度热搜这一条，未获其他源证实**」 |
| 1 源，且是一手/二手可靠源 | 「InfoQ 报道」—— 可信，但仍注明是单一出处 |

**多源 ≠ 独立。** 36氪 和 InfoQ 同时转载同一篇通稿，那是 **1 个**信源不是 2 个。
判断依据是**内容是否雷同**，不是源的数量。

### 4.3 互相矛盾时

两条源说法不一致，**如实说出矛盾，不要挑一条当真**，
更不要折中编一个「大概是这样」。矛盾本身就是结论：
「目前说法不一 —— A 说…，B 说…」。

### 4.4 标题党信号

- 强情绪词：震惊 / 史上最强 / 彻底改变 / 碾压 / 末日
- 纯数字没有主体：「XX 一夜暴涨 300%」
- 只有 `baidu` 一条命中，且 `summary` 为空
- `url` 指向聚合页或内容农场，而不是原文

命中就说「这条措辞偏流量化，建议看原文再判断」——
**但不要因此判它是假的**，标题党不等于假消息。

### 4.5 边界：别把「可信度分级」说成「事实核查」

你**没有**做这几件事，别让措辞暗示你做了：

- 读过正文（你只有 `title` + `summary`）
- 核实过任何数字、日期、人名、金额
- 能力判断一条技术说法在技术上站不站得住

所以：

- 只有标题时写「**标题显示**…」，不脑补正文
- 用户问「这是真的吗」→ **要么读原文再说，要么直说「我只能看到标题，没法核实」**
- **绝不用自己的记忆去"确认"一条当天新闻。** 你的知识有截止日期，
  而这条新闻比它新 —— 这正是最容易自信地编错的地方
- 读原文属**核实**，不在「不越出技能抓数据」的禁令内（那条禁的是给榜单**扩源**）
- **但核实是「被问到时」才做的事，不是速览的默认动作。** 用户问「今天有什么热点」
  时，你要给的是**一份按可信度分级的清单**，不是逐条考据 ——
  每条都去开原文会把一轮 3 次工具调用变成 10 次。
  只有这两种情况值得动手：**用户明确追问某一条**，或**某条数字/结论是整篇回答的支点**
  且明显可疑。其余一律靠措辞（「据 X 报道」「未获其他源证实」）交代清楚就够了。

## 5. 输出的默认结构

用户没指定格式时，用这个（按需裁剪，别硬套）：

```markdown
## 今日 AI 热点（<日期>，N 条）

### 头条
1. **<标题>** — <一句话说明这份内容在讲什么>
   <来源> · <热度/排名> · [链接](url)

### 分类速览
- **模型**：…
- **Agent**：…
- **开源**：…

### 存疑
- <只有单一低信噪源、或标题明显流量化的条目，写清为什么存疑>

### 值得注意
- <跨源同时出现 / 争议 / 与你关注领域相关的条目>
```

### 几条硬要求

- **每条都要有链接。** 没有 URL 的条目直接跳过。
- **说明 > 罗列。** 「36氪报道 X 公司发布了 Y，主打 Z」远好于只贴标题。
- **可信度要体现在措辞里**（§4）：单源写「据…」，多源写「多家报道」，
  矛盾就写矛盾。**别让所有条目看起来一样确定** —— 那等于把 §4 白写了。
- **如实报告失败源。** 有源没取到时在末尾写一句「本次 X、Y 两个源未取到」。
- **别凑数。** 只有 3 条值得说就说 3 条，不要为了显得充实而灌水。
- **报数时把「抓来的条数」和「AI 热点条数」分开说。** `count` 是**抓取条数**，
  不是热点条数 —— 百度热搜、B站热门、Lobsters 是**全品类榜单不是 AI 频道**，
  它们占掉的条数跟 AI 毫无关系。实测 `--since 24h --limit 10` 抓到 61 条，
  其中 **约 42 条（69%）根本不是 AI**（百度 10 条全是时政体育社会、
  B站 6 条全是游戏番剧、Lobsters 6 条全是系统编程），
  AI 相关约 19 条，去掉同一话题的重复后约 15 条。
  **只说「抓到 61 条」然后列出 15 条，用户会以为丢了 46 条数据。**
  要么先讲清楚这个漏斗（「61 条里只有约 19 条和 AI 有关」），
  要么干脆别报原始 count，直接说「筛出 N 条 AI 相关」。
  详细的丢弃理由（去重合并、剔除广告水贴、低信噪源）也应当在措辞里体现，
  别让用户以为遗漏是 bug。
